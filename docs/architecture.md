# Architecture

React/TypeScript runs in the browser. FastAPI runs on Lambda behind an API Gateway HTTP API, and Forum live updates use an API Gateway WebSocket API, so the API keeps no per-process state and scales horizontally (see [scaling](#scaling-the-api-and-live-updates)). Lecture ingestion and Cognito signup validation are separate Lambdas. CloudFront serves the app and lecture JSON from a private S3 origin using OAC. Terraform provisions hosting, API and ingestion; existing CloudFormation stacks retain Cognito and application data. See [deployment](deployment.md) for resource ownership and releases.

![LectureKaki architecture: students reach CloudFront, Cognito, an API Gateway HTTP API in front of a FastAPI Lambda, and an API Gateway WebSocket API that holds live sockets and invokes a forum-live Lambda; FastAPI saves messages and asynchronously invokes a fan-out Lambda to deliver live events. The API uses DynamoDB, S3 forum PDFs and NUSMods; on Mondays, EventBridge Scheduler runs ingestion, which builds lecture snapshots with NUSMods and Bedrock, and the PDF cleanup, which deletes closed rooms' PDFs. CloudWatch alarms on ingestion, cleanup and API errors (Lambda errors, HTTP 5xx and crash logs) and emails the team through SNS. Sign-in is Cognito with an NUS email required.](diagrams/architecture.svg)

## Repository structure

```text
.
├── frontend/
│   └── src/features/        # Discovery, timetable and Forum UI
├── backend/
│   ├── app/
│   │   ├── main.py         # CORS, error handling and router registration
│   │   └── modules/        # Auth, Forum and timetable schemas, rules and data access
│   ├── jobs/lecture_ingest/ # NUSMods fetching, calendar expansion and publication
│   ├── lambdas/pre_signup/ # NUS email signup validation
│   ├── scripts/            # Local ingestion and Lambda packaging
│   └── tests/              # Backend and ingestion tests
├── infra/                  # Existing CloudFormation templates
│   └── terraform/          # Hosting, API, ingestion and deployment-role configuration
├── scripts/smoke_test.py    # API smoke checks
├── docs/                   # Development, architecture and deployment guides
├── .github/workflows/      # CI checks and Terraform deployment
└── compose.yaml            # Local services and test containers
```

Add API features under `app/modules/<feature>/` and register routers in `main.py`. Modules own their data access and expose public interfaces. Jobs/triggers are excluded from the API runtime image.

## Identity and security

![Part 1, static site and sign-in: students load the app through CloudFront from the private S3 web bucket (OAC), sign in with Cognito's hosted pages, where a pre sign-up Lambda allows only @u.nus.edu addresses, and send API requests with their token, which the FastAPI Lambda verifies with Cognito's signing keys.](diagrams/architecture-1-site-and-sign-in.svg)

IAM credentials authorise AWS operations; Cognito accounts authenticate app users. Signup requires an `@u.nus.edu` address and email confirmation.

The [browser flow](../frontend/src/features/forum/auth.ts) uses authorization code flow, S256 PKCE and OAuth `state`. Tokens stay in `sessionStorage`; a non-secret cookie remembers prior login and a `localStorage` revision coordinates logout.

Protect routes with `Depends(get_current_user)` from `app.modules.auth`. The [validator](../backend/app/modules/auth/dependencies.py) checks RS256 signature, expiry, issuer, `client_id`, `token_use=access` and non-empty `sub`. Use that verified `sub` as the user/author ID and enforce ownership separately. ID tokens are not API credentials. Invalid/missing tokens return `401`; unavailable auth configuration/signing keys return `503`.

The [auth template](../infra/auth.yaml) sets access tokens to 15 minutes and refresh tokens to 30 days. Logout clears local tokens, attempts refresh-token revocation and ends the hosted session; issued access tokens can still pass JWT validation until expiry.

## Lecture snapshots and room identity

![Part 4, weekly jobs: on Mondays EventBridge Scheduler runs the ingest Lambda at 03:00, which fetches modules and venues from NUSMods, tags topics with Bedrock and writes a snapshot and then current.json to the S3 web bucket, and the PDF cleanup Lambda at 00:05, which deletes every version of closed rooms' PDFs from the forum PDF bucket.](diagrams/architecture-4-weekly-jobs.svg)

Read `/lectures/current.json`, then use its `path` for `index.json`, `modules.json` (module details, including up to three topics: [title keywords](../backend/jobs/lecture_ingest/topics.py) first, then an [LLM on Bedrock](../backend/jobs/lecture_ingest/llm_topics.py) adds topics from descriptions, cached in `lectures/topic-cache.json`) and `weeks/<label>.json` or `days/<date>.json`. The [publisher](../backend/jobs/lecture_ingest/publish.py) completes the snapshot before switching the pointer. Snapshots use `public, max-age=86400, immutable`; the pointer uses `no-cache`. Empty data is rejected. A re-run of the published semester with under half its sessions is rejected too. A new semester with under half the sessions of the one it replaces is still published (the old term has ended), but logs `SMALL_NEW_SEMESTER`, which raises the `…-ingest-small-new-semester` alarm.

Fields are defined by the [transformer](../backend/jobs/lecture_ingest/transform.py) and [frontend types](../frontend/src/features/discovery/types.ts). Coordinate format changes across producer, consumers and tests. Unknown capacity uses `size=0`; online or unmapped venues use `building=null`.

Only `Lecture` lessons are published, excluding NUS-ISS courses. Session dates and lesson times use Singapore time; `generatedAt` is a UTC ISO timestamp. The [calendar](../backend/jobs/lecture_ingest/academic_calendar.py) covers AY2026/27 Semesters 1–2, holidays and early closures; extend it for later years (see [changeover cases](#weeks-access-and-semester-changes)).

Session IDs are `<moduleCode>-<lessonTypeCode>-<classNo>@<date>-<HHMM>-<venue>`. Preserve class-number leading zeroes and venue slashes. A changed date, start time or venue creates a different occurrence. Forum rooms append `@<acadYear>@<semester>`; URL-encode the whole room ID. The [browser](../frontend/src/features/forum/roomCatalogue.ts) checks an exact current-catalogue match; the backend validates format, date, time and academic year.

### Weeks, access and semester changes

One rule decides what can be reached and when Forum data is deleted: **a lecture's week is open until Sunday 23:59 Singapore time** (weeks run Monday to Sunday). When it ends, that week's discussions close.

- **What users see:** Discover and the Forum list only this week and later ([`weekIsOpen`](../frontend/src/features/forum/roomCatalogue.ts)). An old `?week=` link falls back to the current week. A link to a closed discussion shows "closed", and a discussion that is open on screen closes itself when the week ends.
- **What the API enforces:** [`room_closes_at`](../backend/app/modules/forum/service.py) takes the date from the room ID. A closed room returns no messages and refuses posts, PDF uploads and live-connection tickets with 403, so a hand-made URL cannot bypass the UI.
- **When data is deleted:**
  - **Messages:** `expires_at` and `ttl` are set to the closing time, and DynamoDB TTL removes them (eventually; reads already hide them).
  - **PDFs:** stored as `uploads/<closing date>/<upload id>.pdf`. The [cleanup job](../backend/app/modules/forum/cleanup.py) runs every Monday at 00:05 ([schedule](../infra/terraform/forum_cleanup.tf)) and permanently deletes every version under folders whose date has passed, including uploads that were never posted.
- **Semester changes follow ingestion, not the calendar.** The term shown on Discover and the Forum, and the rooms that are valid, come from `current.json`. The [ingestion job](../backend/jobs/lecture_ingest/academic_calendar.py) publishes the next semester on the first Monday of August (Semester 1) or January (Semester 2). By then every room of the old term is in a past week, so it is already closed and its data deleted. Between terms every week is past, so both pages say the term has ended until the next list is published.
- **Changeover cases:**
  - **Between terms:** after the last week with lectures (Reading week), every week is past until the next semester is published. For AY2026/27 that is 23 Nov 2026 to 3 Jan 2027: Discover says "This term's lectures have ended" and the Forum lists no weeks. Semester 2 is published on Monday 4 Jan 2027, and all its weeks are open (week 1 starts 11 Jan), so people can post ahead.
  - **Next semester's data is late:** if NUSMods has not published it, ingestion rejects the empty result and the site stays on the old term with everything closed. It tries again every Monday of teaching weeks 1–3; [run it manually](deployment.md#publish-frontend-and-lectures) once the data is out. If the new semester is published with under half the previous semester's sessions, the `…-ingest-small-new-semester` alarm emails the team: check NUSMods and re-run ingestion once its data is complete.
  - **Summer (May to July):** [`semester_for`](../backend/jobs/lecture_ingest/academic_calendar.py) keeps Semester 2, so the site shows it with every week closed. Special terms are not ingested: their lessons have no teaching-week numbers, and some have no lessons at all.
  - **The calendar runs out:** `SEMESTERS` only lists AY2026/27. From August 2027, ingestion fails with "No calendar entry…" and the ingest alarm fires; the site stays on Semester 2, all closed, until the next year's start and last days, holidays and early closures are added.
  - **Where start dates come from:** the NUSMods API has no semester dates. Semester 1 and 2 lessons give week numbers, and special-term lessons give exact dates or nothing. NUSMods keeps each term's start date by hand in [`academic-calendar.json`](https://github.com/nusmodifications/nusmods/blob/master/packages/nusmods-academic-calendar/academic-calendar.json) (MIT, updated each June or July). It only has start dates, so our calendar is still needed for recess and reading weeks, exam periods and holidays.
  - **Known gaps between terms:** Discover's ended-term message does not name the term (the Forum still shows "Semester 1"), and a closed discussion link still shows a Retry button, which cannot help.

## Search

Search runs in the browser; neither search calls the API.

- **Discover:** the query is split into words. A lecture matches when every word appears, in any order, in its module's code, title, description or topics ([`filterSessions`](../frontend/src/features/discovery/discoveryFilters.ts)). Venues and cross-listed codes are not searched; use the Buildings and Subject codes filters. Results stay grouped by day. Within each day, [`rankWithinDays`](../frontend/src/features/discovery/discoveryFilters.ts) orders matches best first, then by start time:
  1. The code starts with the query (spaces ignored).
  2. The title starts with the query.
  3. Every word starts a word in the title, or starts the code.
  4. Every word appears in the code or title.
  5. Every word appears in the code, title or topics.
  6. Only the description matches.
- **Add a module (Timetable):** [`searchModules`](../frontend/src/features/timetable/moduleSearch.ts) filters NUSMods' `moduleList.json` for the selected academic year to modules offered in the selected semester whose code or title contains every word. It ranks an exact code first, then the same tiers as Discover without topics or descriptions, then by code. The page shows 20 results at a time.

## Persistence and live updates

![Part 2, REST API and storage: students call the API Gateway HTTP API, which invokes the FastAPI Lambda; FastAPI reads and writes the three DynamoDB tables, issues signed URLs for and validates or deletes forum PDFs, and checks timetables against NUSMods. Browsers upload and download PDFs directly with signed URLs and fetch the NUSMods module list themselves.](diagrams/architecture-2-rest-api-and-storage.svg)

- **Timetables:** the [UI](../frontend/src/features/timetable/TimetablePage.tsx) loads/saves a four-semester book through `/timetable/semesters` and keeps local selections. The [API](../backend/app/modules/timetable/api.py) validates selections against NUSMods. The [repository](../backend/app/modules/timetable/repository.py) stores one record per Cognito `sub`, with last-write-wins replacement. Legacy `/timetable` routes remain supported.
- **Interest topics:** an ordered list. On [Profile](../frontend/src/features/profile/ProfilePage.tsx), new picks go to the end and can be reordered or removed. Signed in, the list is saved through `PUT /profile/topics`, and the API keeps the order (it only drops duplicates). Signed out, it is saved in the browser's `localStorage` (`lecturekaki:topics:v1`). On sign-in, browser topics are copied to an account that has none; otherwise the account's list wins, and the browser copy is kept for when the user signs out. The [sidebar](../frontend/src/features/profile/SidebarTopics.tsx) shows the first five, or three suggestions if none are picked. Discover's "Only my topics" uses the whole list. Both follow saves immediately through `subscribeToTopicUpdates` in [profileApi](../frontend/src/features/profile/profileApi.ts).
- **Forum:** authenticated HTTP reads/creates messages and allows author-only deletion. Messages allow 1–500 characters. A discussion closes when its lecture's week ends, and its messages and PDFs are deleted then; see [Weeks, access and semester changes](#weeks-access-and-semester-changes). Records use `ROOM#<room_id>` / `MSG#<message_id>`; DynamoDB TTL on `ttl` performs eventual cleanup. See [schemas](../backend/app/modules/forum/schemas.py) and [service](../backend/app/modules/forum/service.py).
- **WebSockets:** request `POST /rooms/{room_id}/connection-ticket` with the Bearer access token, then open the returned `path`. Deployed, it is the API Gateway WebSocket URL, `wss://<id>.execute-api.<region>.amazonaws.com/live?room=...&ticket=...`; locally (no `FORUM_WEBSOCKET_URL`) it is `/rooms/{room_id}/live?ticket=...` on the API's own origin. After opening, the client sends `ready`, waits for acknowledgement, then refreshes history before showing connected. Posting/deletion remain authenticated HTTP operations. See [routes](../backend/app/modules/forum/api.py), [gateway delivery](../backend/app/modules/forum/gateway.py) and [client](../frontend/src/features/forum/forumSocket.ts).
- Tickets are room-bound, single-use and valid for at most 30 seconds; hashed records use `TICKET#<hash>` / `METADATA`. Pending connections use `CONN#<connectionId>` / `METADATA`; only the readiness handshake adds `ROOM#<room_id>` / `CONN#<connectionId>` membership for broadcasts. Records expire with the original access token; the client rotates the socket before then and reconnects if acknowledgement fails. The in-memory [room hub](../backend/app/modules/forum/realtime.py) is only for local development, where it requires one process.

## Scaling the API and live updates

![Part 3, live Forum updates: students hold a WebSocket through API Gateway, whose forum-live Lambda records connections in DynamoDB after the ready handshake. Posting goes through the HTTP API to FastAPI, which saves the message and asynchronously invokes the fan-out Lambda; fan-out reads the room's connections and sends the event to each one through the WebSocket API.](diagrams/architecture-3-live-forum-updates.svg)

API Gateway holds WebSocket connections; DynamoDB stores room membership. This removes the former single-process broadcast restriction. FastAPI handles HTTP requests on Lambda, while a separate asynchronous Lambda broadcasts to ready connections. No always-on server, shared broker or application load balancer is required.

| Function                   | Responsibility                                                              |
| -------------------------- | --------------------------------------------------------------------------- |
| HTTP API → FastAPI         | Authenticate requests, read/write application data and enqueue live events. |
| WebSocket API → forum live | Validate tickets, acknowledge readiness and manage connection records.      |
| Asynchronous fan-out       | Query room membership, deliver events and retry transient failures.         |

- **Entry points:** [`app/aws_lambda.py`](../backend/app/aws_lambda.py) exposes the three handlers. Mangum adapts HTTP API events to FastAPI; [`gateway.py`](../backend/app/modules/forum/gateway.py) handles WebSocket events and broadcasts.
- **Delivery:** [`delivery.py`](../backend/app/modules/forum/delivery.py) enqueues broadcasts after HTTP writes commit. The worker uses bounded SDK calls, retries transient failures and reports exhausted failures through SNS. Enqueue failures are logged and alarmed without failing a committed write. A crash between saving and enqueueing can still lose a notification; stored history remains authoritative.
- **Local mode:** leave `FORUM_WEBSOCKET_URL` and `FORUM_FANOUT_FUNCTION` empty. Tickets point at `/rooms/{id}/live` and the in-memory hub uses the same readiness handshake. Local live delivery requires one process.
- **Infrastructure:** [`api.tf`](../infra/terraform/api.tf) defines the three Lambdas, their roles, HTTP/WebSocket APIs, retries and alarms ([what each alarm means](deployment.md#alerts)). Packaging and releases are covered in [deployment](deployment.md).

Release the backend and frontend from the same revision because both implement the readiness handshake. The client merges duplicate events by message ID and keeps deletion markers so delayed creates cannot restore deleted messages.

Fan-out work grows with recipients: each broadcast queries room membership and calls `PostToConnection` for each ready connection. Background delivery keeps this work outside the HTTP request. Costs follow HTTP requests, Lambda execution, WebSocket connection-minutes and deliveries; storage and logs also incur charges. See current [API Gateway](https://aws.amazon.com/api-gateway/pricing/) and [Lambda](https://aws.amazon.com/lambda/pricing/) prices.

The WebSocket API limits connections to two hours with a ten-minute idle timeout. The client pings every four minutes and rotates before access-token expiry. HTTP requests have a 30-second integration limit; Lambda concurrency and connection-rate quotas also bound capacity. Verify expected load and recovery behaviour before making availability or capacity claims.
